# Port a calculation into azoth

azoth's one priority is finishing the port of NeqSim. A new calculation is not a
function someone adds — it is a **spec plus two hand-written kernels plus a test**,
with every other file generated from the spec. This skill is the whole of that
discipline.

## When to Use

- When a NeqSim calculation is to be ported: a property, a coefficient, a flash or a
  unit operation.
- When the manifest (`databank/manifest.toml`) names a `not-yet` column and its NeqSim
  class is to be closed.
- When a spec, kernel, or generated file disagrees with the specification.

Do not use this skill to *call* a calculation — that is `azoth-run-calculation`.

## Inputs

- The NeqSim class and the paper for the method.
- The spec's declared inputs, outputs, units, valid range, assumptions and cases.

## Outputs

- One `specs/calcs/<namespace>/<id>.toml` (or `specs/models/` / `specs/cases/` for a
  procedure).
- One Rust kernel and one Python kernel — two hand-written implementations of the same
  arithmetic.
- One test comparing the two case by case, with matching iteration counts.

## How a calculation runs

The port is a pipeline, and CI regenerates everything and fails on a diff:

```text
specs/**/*.toml ─► tools/gen_registry.py ─► crates/*/spec_gen.rs, python/_registry_gen.py
                ─► tools/gen_models.py  ─► crates/azoth-eos/model_gen.rs, python/_models_gen.py
                ─► tools/gen_vocabulary.py
                ─► tools/gen_docs.py    ─► docs/src/**, SUMMARY.md
                ─► tools/gen_stub.py    ─► python/src/azoth/_core.pyi
```

The spec declares; the generators name. A field the spec does not name cannot be
emitted, and a declared output with no field is a promise the code cannot keep —
`python/tests/test_registry_contract.py` holds both directions.

## Python usage pattern

```python
# A new calculation costs four hand-written files. The spec declares; the two kernels
# implement; the test compares. Everything else is generated from the spec.
import azoth

azoth.available()  # what the registry already knows, before adding to it
```

## The keycard

Not applicable: a port adds a calculation, not data. Where the new calculation reads a
coefficient, its spec declares the unit and the keycard's `coefficients` section
supplies it — the port does not hard-code a constant the keycard should carry.

## Validation checklist

- [ ] The spec names a paper, a NeqSim class, and its own notes — and does **not**
      upgrade `verification.status` past `unverified`.
- [ ] The two kernels run the same arithmetic and agree case by case, by tolerance and
      matching iteration counts.
- [ ] Every generated file is regenerated, and `git diff` is empty.
- [ ] `databank/manifest.toml` records the columns this tranche closes.

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| A value looks right everywhere | A constant copied from NeqSim, not the paper | Cite the paper; ship `unverified` |
| Two answers for one call | The two kernels differ subtly | Compare by tolerance, not bit-equality |
| A generated file silently stale | Regenerated by hand, then drifted | Run the generators; CI fails on diff |
| A field silently ignored | The spec does not declare it | Declare it in the spec first |

## Limitations

A port is accepted on azoth's own tests, never on its provenance. That NeqSim
implements something is evidence it can be implemented, not evidence it is right.
Reading someone's Java is not reading the paper, so everything ported ships
`unverified` until someone reads the paper.
